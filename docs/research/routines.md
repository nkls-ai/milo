# Routines: how others store and replay agent work

Written 2026-10-30 for Phase 2 item 5 of the [roadmap](../ROADMAP.md): "remember how to do this, call it the Monday report", then do it again on request or on a schedule. This note covers what other projects do, what Milo takes from them and what it leaves.

## What others do

| Project | What gets stored | Inputs | Replay | When the UI changed | License |
|---|---|---|---|---|---|
| [browser-use/workflow-use](https://github.com/browser-use/workflow-use) | A JSON workflow per task (`workflows/<id>.workflow.json`) with a metadata index. "Generation mode" runs the agent once and turns its *execution history* into a workflow with parameters. | Variables in the JSON, filled per run, also from a prompt (`run-as-tool`) | Deterministic steps (selectors), no model | A failing step falls back to the browser-use agent ("self-healing") | AGPL-3.0 |

## What we learned

1. **Instructions beat recorded clicks for a person's own Mac.** The deterministic replays (workflow-use, OpenAdapt) are fast and cheap, but they need a fallback agent or a repair step the moment a button moves. The record-and-replay skills and Codex both end up writing instructions in words for an agent and treat the recording only as evidence. Milo's worker already chooses the route on each run (scripts first, then the accessibility tree, then clicks, see [ADR 14](../adr/0014-scripts-milo-writes-and-short-questions.md)), so a recipe in words keeps working when a menu moves. The roadmap already said the same.
2. **Make the recipe from a run that worked.** workflow-use's generation mode and OpenAdapt's "explore" both start from an agent run that succeeded. Milo has that run already: the helper's task text and its steps in the transcript (titles plus the exact commands and tool calls). A Codex or Claude worker turns them into a recipe. Nothing is recorded beyond what the Milo window already shows.
3. **Concrete values become named inputs with a question and a default.** Every system has parameters. Skills name them (`arguments`), Codex asks for "the values that change between runs". Milo's inputs also carry the question to ask ("Which month?") and a default in words ("last month"), which the worker resolves against the date it gets with every task.
4. **Checks after steps, and stop before the consequential step.** OpenAdapt's numbers make the point: a "saved" message on screen proved nothing in 54 of 72 bad saves, and only reading the record back caught them. Its repair mode stops *before* the save. Milo's recipes say what should be true after each step, and a routine run that finds the world different stops and asks instead of improvising. Sending, deleting and overwriting keep asking as always ([ADR 9](../adr/0009-approvals-and-action-levels.md)): saving a routine approves no destructive step ahead of time.
5. **Plain Markdown with front matter, like SKILL.md.** People and agents both already read and write it. Only the name and a one-line description need to sit in the talker's prompt; the body is read when the routine runs (progressive disclosure, as in Claude skills).
6. **Missed runs: one catch-up, not a pile.** launchd runs a missed calendar job once at wake. Milo does the same within a grace window and otherwise says it missed the run, so a Mac that slept through the weekend doesn't start a Saturday report on Monday evening.
7. **Ask before running unattended when something changed.** Shortcuts lets the user choose "ask before running" per automation. Milo asks before a scheduled or spoken run whenever the recipe changed since the user approved it (a hand edit, or a worker writing into the folder), and never otherwise.

## Choices

- **Format.** `~/Milo/routines/<slug>.md`: front matter (`name`, `description`, `inputs` with `ask` and `default`, `schedule`, `apps`, `paused`, `last_run`, `version`), then `## Goal`, `## Steps` (each step with a `Check:` line), `## Ask first`. The front matter is a small subset of YAML (`key: value`, `[a, b]` lists, a list of input blocks) that Milo parses itself with the standard library ([ADR 4](../adr/0004-dependencies.md)). A full YAML parser would also turn `no` into false and `09:00` into a number.
- **No code adopted.** workflow-use and Skyvern are AGPL-3.0, so nothing is copied from them. The MIT projects (OpenAdapt, open-record-replay, record-and-replay-skill) informed the design. Their code solves recording and deterministic replay, which Milo doesn't do.
- **Schedules in plain words.** "every Monday at 9", "every weekday at 8:30", "every day at 18:00", "on the 1st of every month at 9". The talker writes them in that English form whatever language the user speaks. The heartbeat checks them every tick with no model call ([ADR 3](../adr/0003-zero-token-heartbeat.md)).
- **Later.** Watching the user do it once (an accessibility event stream like open-record-replay's), deterministic fast paths for steps that never change, and reading the result back from the app (OpenAdapt's read-back) as a built-in check rather than the worker's own.
