# Milo architecture

Milo is two processes on one Mac:

- **The app** (`app/`, Swift). The floating character, speech bubble, push-to-talk keys, pasting dictated text into the focused app, the Milo window with the conversation, and the menu bar item. It holds the Accessibility and Screen Recording permissions, so it also reads windows, takes screenshots and runs the worker's actions on the Mac. It knows nothing about models.
- **The brain** (`brain/`, Python, run with `uv`). Microphone, speech-to-text, the live chat model, the agent harness, text-to-speech, memory and the heartbeat.

They talk over a Unix socket at `~/Milo/run/brain.sock` (mode 0600) using JSON objects, one per line. Every message is listed in [`protocol/messages.json`](../protocol/messages.json) and defined in `brain/src/milo/core/events.py`. Both test suites decode that file, so the two sides can't drift apart silently.

Events that only draw (state, bubble, levels) go to every connected app. Requests that need one app to act and answer (`look_request`, `hands_request`, `app_request`) go to the newest connection only (`AppLink`), and if that app hangs up, what it still owed fails at once.

Only one brain runs per workspace. It takes an `flock` on `~/Milo/run/brain.lock` before it loads anything and holds it until the process ends, and a second brain exits at once. The app starts a brain only while nobody holds that lock: after a restart it waits for the old brain to let go, and it leaves a brain started by hand alone. It stops its brain with SIGTERM, since `uv run` passes that on and swallows SIGINT. Two brains would each load Whisper and OmniVoice, which on 16 GB fills swap and makes every Whisper pass several times slower.

`~/Milo/` is the workspace. It holds `config.toml`, Milo's persona for the chat model (`persona.md`), the agent's instructions (`AGENTS.md`, `CLAUDE.md`), `memory/`, `reminders.md`, `dictionary.md`, `state/` and `logs/`. The harness runs in `work/`, the one folder of the workspace its sandbox may write. It can read the rest, but Milo's control files (config, persona, instructions, reminders, the dictation dictionary, routines, memory, secrets) change only through the Settings window, Milo's tags and tools that ask the user ([ADR 20](adr/0020-helpers-never-write-milos-control-files.md)).

Rules that keep the parts swappable:

1. **Services depend on ports, never on adapters.** `services/` imports from `milo.core` only. A service gets every collaborator through its constructor.
2. **Adapters register themselves.** `@HARNESSES.register("codex")` sits next to the class. `milo.adapters.load_builtin()` imports the built-in modules. Adding an engine means adding a module, without editing any switch statement.
3. **Config picks by name.** Every swappable section has `use = "<name>"` and a table `[<section>.<name>]` holding that implementation's options. An adapter parses its own table with `options_from(OptionsDataclass, table, "section.name")`, which rejects unknown keys.
4. **Only `compose.py` wires concrete things.** Tests wire fakes from `tests/fakes.py` instead. `tests/services/stack.py` runs STT, TTS and memory inline, so most tests are deterministic. `Stack(real_threads=True)` puts each on a real thread, as compose does, and `tests/test_races.py` uses it with the real socket and slow engines to catch ordering bugs between the loop and those threads.
5. **Blocking work runs on dedicated single-thread executors.** STT gets one thread and TTS another, so MLX and PyTorch each stay on their own thread and the event loop never blocks.
6. **"Is the user busy?" has one answer.** `services/attention.py` holds the facts (a turn runs, the mic records, Milo speaks, a question waits, a helper works) and named questions over them: `in_conversation`, `using_voice`, `occupied`, `at_work`, `private`, `user_speaking`. compose.py passes the question a service needs, never its own mix.

## Portability

Milo runs on macOS only, but the brain's core and the protocol must not depend on it, so a Windows or Linux app can drive the same brain later ([ADR 27](adr/0027-a-platform-boundary.md)). macOS belongs in brain adapters and in the app's adapters behind `app/Sources/MiloKit/Ports.swift`. Adapters are picked by name in `config.toml`; a part that leaves `use` out gets the `Platform`'s engine (`core/platform.py`), and `adapters/platform.py` is the one place that asks which OS this is. On a Mac that is today's set (mlx_whisper, omnivoice with `say` behind it, mlx_e5, the mac connections); on Linux and Windows it is ElevenLabs for hearing and voice, the hash embedder, no fallback voice and no connections, until they have local engines. The workspace template names no Mac engine for that reason. POSIX calls (`flock`, uids and modes, process groups, Unix sockets) go through `milo.system`, one module per OS family. Apple-only packages (`mlx`, `mlx-whisper`) carry a `sys_platform == 'darwin'` marker, so `uv sync` works on Linux and Windows. On the wire go plain words, opaque ids and top-left global points, never native enums or key codes. `brain/tests/test_portability.py` reads every core module (`core`, `services`, `memory`, `proactive`, `connect`, `transport` and the top-level modules) and fails on a new macOS or POSIX coupling: AppleScript, bundle ids, macOS paths and commands, ⌘ keys, System Settings, Apple frameworks and apps, "Mac" in what the user or the model reads, `fcntl` and `AF_UNIX`, `%-d`-style strftime flags (use `core/words/dates.py`), `sys.platform`. Its `ALLOWED` list holds today's 54 exceptions in 29 files, each with its reason. It is the to-do list for a port, and it can only get shorter: a line that no longer matches fails, `CEILING` holds the count and only goes down, and a line added past it needs a `GROWN` entry saying why it can't move. A test checks that this paragraph states the count.

For every new feature:

- An OS call in the brain goes into an adapter behind a port. Services get the port.
- Core strings the user or the model reads don't say "Mac", "⌘" or "System Settings". Use neutral words, or let the app write its platform's text, as it does for permission errors.
- An app the brain must know goes in one place under a canonical key (today `core/types._BUNDLES`), not as a bundle id in a service.
- A worker tool is named for what it does, not for the API behind it (`run_script` with a language, not more AppleScript-only tools).
- A protocol field carries plain words (`button`, not `AXButton`), opaque ids the brain only echoes back (`pid`, `window`) or top-left global points.
- Key combos and risk words are data that say what a key or a label means on that platform.
- In the app, logic goes in `MiloKit` files that import only Foundation or Combine. AppKit, AX, CGEvent and ScreenCaptureKit go in `Adapters/` or `AppKit/`.
- An Apple-only Python package gets a `sys_platform == 'darwin'` marker and is imported only inside its adapter's methods.
- An OS call the core can't avoid (a lock, a socket, a process, file ownership) is a function in `milo.system`, written for POSIX and stubbed for Windows. A new default engine goes in `adapters/platform.py`, not in the template or `config.py`.
- Dates in text are `core/words/dates.py`'s words, never `%-d` or a locale's `%A`/`%B`. A line Milo says goes in `core/words` under a key, with English and, where it exists, German. Times read from files, the app or the model go through `core/times.py`.
- The machine's name in text is `Platform.computer`, not "Mac".

### Porting guide

What a Windows or Linux Milo still needs, most work first. The brain resolves its dependencies for Linux and Windows and imports without the Apple-only packages, and `.github/workflows/brain.yml` runs its tests on Ubuntu; talking works with `[chat]` on Claude or any `openai_compat` provider and ElevenLabs for hearing and voice.

1. **A native shell.** The app is the whole face of Milo and none of it runs outside Apple's frameworks: the overlay panel and the wren (CALayer, `WrenView`, `FlightDriver`), the bubble, the Milo window, settings and setup. On Windows: C# with WPF (a layered, topmost, click-through window) and the wren drawn again in Composition or Win2D from `WrenPose` and `WrenRig`'s numbers. It ports `MiloController`, `MiloModel`, `Presence`, `TakeoverDetector`, `ScreenController` and `Delivery` from `MiloKit` and speaks `protocol/messages.json`, with `app_hello` (ADR 27) once the brain reads it.
2. **Hands.** `MacHands`, `Accessibility` and `MacWindowWatcher` become UI Automation (Invoke, Value, Text and Scroll patterns), `SendInput` for borrowed input, Windows.Graphics.Capture for screenshots and `SetWinEventHook` for the window outline; on Linux AT-SPI2, XTest or libei, and the ScreenCast portal. Which apps take what in the background has to be found out again, app by app. The brain side: `run_script` with PowerShell in place of `run_applescript`, the `ScriptDialect` port for `sheets.py` and `documents.py` (Excel through COM), and the risk data per platform (Recycle Bin, Shift+Delete, Outlook's send keys).
3. **Push-to-talk and paste.** A low-level keyboard hook for a bare modifier (`right_ctrl`, `right_alt`), the clipboard and `SendInput` Ctrl+V, and reading the field back for ADR 21 through UI Automation. Wayland mostly can't do the bare-modifier key or the overlay.
4. **The EventKit replacement and connections.** Calendar and Reminders run in the Mac app through EventKit; elsewhere a `connect.outlook` adapter (Outlook COM or Microsoft Graph) or Evolution Data Server / CalDAV, plus mail, notes and files (Windows Search). Until one exists, the platform's connections are `none` and the worker gets none of those tools. The brain itself (quick actions, `<today>`, the brief, meeting notes) reaches Calendar, Reminders and the player through the same `Calendar`, `Reminders` and `Music` ports (`services/connections.py`), so one adapter serves both; an app that holds them can instead answer the same `app_request` ops `core/app_connections.py` sends.
5. **The brain's Windows primitives.** `brain/src/milo/system/windows.py`: named pipes with a DACL for the three sockets, a named mutex for the lock, owner SIDs and DACLs for secrets, Job Objects for the harness CLIs and their trees. Each stub says what to use. Also `adapters/region.py` (GetUserDefaultLocaleName) and `adapters/power.py` (no `pmset`).
6. **Local engines.** A `stt.faster_whisper` or `stt.whisper_cpp` adapter (the quick-pass timing here was tuned on MLX and needs measuring again), an ONNX e5 embedder, OmniVoice on `cuda` or `cpu` (`device = ""` picks), and Piper as the offline fallback voice. Each goes into `adapters/platform.py` as that OS's default once it exists.
7. **Meeting audio.** WASAPI process loopback on Windows 10 2004 and later, PipeWire monitor streams on Linux.
8. **Words.** Twelve core files still say "Mac" in what the user or the model reads, and more name Mac apps (Finder, Numbers, Safari) or System Settings. Most of what Milo says comes from `core/words` (ADR 34), and `Platform.computer` names the machine in the talker's prompt, routines and task questions ("Mac" on a Mac, "computer" elsewhere); the rest should move there or to the app. `test_portability.py`'s `ALLOWED` lists every one.

## Listening

Both keys listen the same way (`services/listening.py`, `services/live_transcript.py`). Only what happens to the text differs: dictation pastes it, talk hands it to `LiveTalk`.

1. **Phrases.** While the key is held, `LiveTranscript` reads the new audio every 0.1 s and `PauseSegmenter` cuts it into phrases at pauses: 0.7 s of quiet, or 0.3 s once a phrase has run 6 s, or the quietest frame once it reaches 12 s. Speech is anything 2.5 times above the room's floor, but at least 0.004 RMS, so a microphone far away still makes phrases and live words.
2. **Commits.** Each closed phrase that no guess holds (step 3) is transcribed by the full model (large-v3-turbo, full 30 s window) while the user goes on talking. That text is final. `stream = "type"` pastes it at once. The text before a phrase only keeps its language (a short "okay" can't be detected reliably); it is not put in Whisper's prompt, which made more errors on test dictations because Whisper copies the prompt's style.
3. **Guess.** When the open phrase has been quiet for 0.25 s, the full model transcribes it as it stands, in a quick pass (below). If the user speaks again, the guess is dropped. If they let go first, the guess is the end and the release costs no pass at all. If the pause goes on and closes the phrase, the guess is its commit too, as long as nothing voiced lies outside it: the same model has heard the same audio, and a second pass with the full window would keep the STT thread busy for 3 s per phrase on a loaded Mac, holding up live words and the release.
4. **Preview.** Otherwise the small model (whisper-base) re-reads the open phrase for the live words above Milo (`partial`). Commits and guesses always go first, so at most one preview pass (about 0.05 s) runs ahead of the full model.
5. **Release.** `finish()` interrupts a commit or preview in flight (`Transcriber.interrupt()`: the Whisper encoder runs four layers at a time and checks between them). A guess in flight is let finish if nothing was said after it. Then everything not yet committed, closed phrases and the open one, goes in one quick pass, unless a guess holds all of it.

**No word is lost.** The speech threshold is made for finding pauses, and a soft voice can stay under it: trailing off, a quiet microphone. Until 30 October such words were dropped: after a guess (its end never moved), in a tail after a commit, and in a soft phrase between pauses. `PauseSegmenter.voiced()` is a lenient second check, a little above the room's floor, and it decides what holds words: each phrase runs from the end of the one before, trimmed only up to the first voiced frame; a guess only stands if nothing voiced lies outside it; a pause is only cut where it is truly quiet, never through soft words; a quick pass that hears nothing in voiced audio is done again at full accuracy. Last, a safety net: text with fewer than 1.5 words per second of speech (test dictations had 3.5 to 7) gets one full pass over the whole recording, and that text wins if it has more words.

**The next key press doesn't wait.** The brain reads the app's commands one at a time. `release()` stops the mic, hands the recording to a task and returns, so a key pressed right after a release opens the mic at once and approval clicks aren't held up. Each recording's results (typed phrases, the paste, the talk turn) go out only after those of the recording before it (`_InOrder`), and only the newest release puts Milo back to rest. The app shows the recording 80 ms after key-down (`PushToTalk.showAfter`); a press shorter than 250 ms is still a tap, so a double tap locks hands-free.

The key going down first queues `Transcriber.wake()`: a short pass over a second of silence on each loaded model. On a 16 GB Mac with a browser and a few agents open, macOS pages an idle brain's 5 GB of model memory out, and the first pass after that took 3.8 s for 2 s of speech. Waking at key-down pages the models back in while the user is still talking. A wake that takes over half a second is logged.

All passes run one at a time on the STT thread. A quick pass encodes the audio plus 1 s of silence, but at least 10 s, instead of a padded 30 s window, so it costs roughly its own length (0.3 s for a short phrase on an idle M3 against 1.1 s). With less than 10 s the decoder loses track of where speech ends and repeats itself; a quick decode that loops, runs past 8 tokens a second or that Whisper itself doubts goes through the full window instead. Previews never do: their text is replaced by the next pass anyway, so an unsure preview shows as it is and one that loops shows nothing (`mlx_whisper.doubt`, [ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). The "looks wrong" log line names the model. Quick passes on single phrases missed a few more words than full windows (on 48 test phrases 2.7% against 1.7%), but on whole test dictations, phrase by phrase, they made fewer errors than one full pass over the recording (0.4% against 1.6%). `stream = "off"` runs no live passes and transcribes the whole recording on release with full windows.

**Measured** with `scripts/e2e-dictation.sh` (macOS voices replayed in real time into a real brain, on an M3 with 16 GB while a browser and several agents ran: load average 20 to 25, the models paged out between dictations). Release to paste, `preview` against `off`: 2 s dictations 0.41 to 1.41 s (2.8 to 4.7 s), 15 s 0.25 to 0.75 s (3.1 to 4.7 s), 60 s 0.86 and 1.29 s (14.5 to 15.9 s). The first live words came 0.4 to 1.6 s after speech began, the listening state 80 ms after key-down. Not one word of 488 was lost (word error 0.4%); `off` lost 6 (1.6%). What is left of the release is one quick pass, 0.4 s for a short phrase on a quiet Mac and up to 1.4 s on this loaded one. Before these changes (main at 5a5b284) the same run pasted after 0.80 to 2.31 s.

**Learning from fixes** ([ADR 21](adr/0021-dictation-learns-from-your-fixes.md)). After a paste the app's `PasteWatcher` (`app/Sources/MiloKit/Dictation/`) reads the focused field through `AXFocusedText` 0.3 s later and then every 0.5 s, for up to 45 s or until the focus moves, the span is gone or Milo pastes elsewhere. It finds the pasted words between 24-character anchors (`PastedSpan`), and at the end `CorrectionDiff` keeps only small fixes: 1 to 3 words for 1 to 3, spelled alike, not a capital at a sentence start, not a change between two real words or two weekdays. Only those pairs go to the brain (`dictation_fixed`); password fields, password apps and fields over 100,000 characters are never read, and nothing is read while `[dictation] learn` is off. The brain's `Corrections` counts them in `~/Milo/dictionary.md` (`MarkdownDictionary`), says "Learned: …" in the bubble the first time unless Milo is busy, and hands every learned word to the transcribers through the `Vocabulary` port (Whisper's prompt after `[stt.mlx_whisper] vocabulary`, Scribe's keyterms). `DictationFixes` wraps the dictation cleaner and replaces heard words with meant ones before the paste: always for a line the user wrote, after one sighting for a name, after two otherwise. `Listening` calls `Corrections.refresh` when a key goes down, so a hand edit of the file reaches Whisper with one `stat()`. Settings › Dictation has the switch and "Show the words"; the menu bar has "Dictation words…".

The menu bar item's "Dictation style" changes `[dictation] stream` the way the Settings window does (`set_setting`, see Settings below): the brain saves it and uses it from the next recording. The menu ticks the value from the brain's last `settings`, which the brain also sends on connect.

## A user turn

Typed and spoken turns take the same path through `LiveTalk`:

1. **Chat model.** `[chat] use = "claude_live"` keeps one `claude -p --input-format stream-json` process running with no tools. Its system prompt is `persona.md`, the reply rules, the memory rules, the always-on facts (the basics and pinned ones). Milo's open reminders from `reminders.md` go in the `<today>` block instead, which a user message carries when it changed, so setting a reminder doesn't change the cached prompt. Each turn then carries a `<memory>` block in front of the user's words: what `TurnMemory.before_turn()` recalled for it (see Memory below). The recall, the `<meeting>` block and the `<today>` block are fetched together (`asyncio.gather`), not one after the other. The system prompt is built again on every press of the talk key to see whether the conversation is still fresh, so `persona.md` and `profile.md` are read again only when they changed (`memory/text_file.TextFile`), as `reminders.md` already was. The conversation stays open between turns. After `[chat] conversation_idle_reset_s` (600 s) of silence the next turn starts a fresh one, which also reloads the persona and profile. A conversation started but not used yet goes stale after the same time, counted from its start. The model's prompt cache lasts about 5 minutes, so a longer reset or a keep-warm ping wouldn't pay ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). At boot `server.py` warms it, so the first turn skips the process start. A fresh process also gets one throwaway priming turn in the background, because the first real turn on a new process takes 2 to 3 s to its first word and the second about 0.5 to 1 s. And the talk key going down starts a due fresh conversation (`LiveTalk.prepare()`), so the start hides behind the user's own words.
2. **Reply stream.** Each user message is prefixed with `[weekday date time, frontmost app: X, language: English]`. The language is what the transcriber heard (Scribe's `language_code`, Whisper's detection), else a guess from the words (`core/language.detect`), else the message before's; the reply rules say to answer in exactly that language whatever the memories are in, and `SpokenLanguage` passes it on to helpers (`say` in that language), to every screen question, borrow, task, remember, remind and open question and to Approvals' own lines, which have German words (the connection tools' questions are still English) ([ADR 28](adr/0028-open-at-once-and-answer-in-the-users-language.md)). The model starts its reply with an emotion tag such as `[happy]` and may add `<open app="Google Chrome" url="https://www.youtube.com"/>` (right after the emotion tag), `<remember>fact</remember>`, `<reminder>YYYY-MM-DD HH:MM text</reminder>`, `<task title="..." screen="yes|no">description</task>`, `<steer helper="2">change</steer>`, `<stop helper="2"/>`, the act tags (Quick actions below) and `<write>` (Writing where you are below). `ReplyParser` reads the text deltas as they arrive, sets the face once the emotion is known, holds back anything that could still turn into a tag, and passes the rest on as speech. The first sentence goes out as it comes; after it, text is passed on up to the last finished sentence that isn't a question. When the reply set a tag that does something (any but `<look>` and `<title>`), a question at its end is dropped, so "Done. Anything else?" says "Done." The reply rules ask for one sentence of about 15 words for small talk and no question at the end unless the answer is needed ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). An `<open>` is acted on the moment it closes, while the reply still streams: `Opener` sends the app `open_url`, `open_app` or `open_file` and logs how long it took from the user's words. An app always opens; an address or file opens without a yes only when the conversation read no outside text or (for an address) the user's own words name that site's front page at its own address (`named_by`), otherwise Milo asks "Open evil.example?" after the reply. An act tag starts the same way, the moment it closes. When the stream ends, LiveTalk saves facts to the profile and reminders to `reminders.md`, and hands tasks, steers and stops to the `Orchestrator`.

   **What waits for a yes** is one `TagPolicy` per reply (`services/tag_policy.py`), worked out when the reply starts. Once the conversation has read outside text (a task result, a look, meeting words, an untrusted memory, another person's line in `<today>`), or the message itself carries it, every tag that takes effect at once waits: an `<open>` of an address or a file the user's words didn't name (the user's last three messages), an act, `<remember>` and `<reminder>`, and `<write>` goes in only when the user's words asked for writing. In auto mode at the Mac a reminder and an act go ahead anyway (`TagPolicy.ask_reminder`, `ask_acts`): each has its card and Undo, and what can't be undone or reaches other people still asks in QuickActions and Approvals ([ADR 35](adr/0035-small-things-just-happen.md)). An address goes ahead only when the user's own message asks for something (`asks_for_work`, `ask_open`, ADR 28): a reply to "thanks" after a mail still asks, since an address can carry data out. When Milo's last reply was a question, the user's answer is read after the request it answers ("put lunch in tomorrow", "What time?", "at one"), so it counts as their own request (`LiveTalk._take_request`). A task, a steer or a routine from such a reply runs careful, unless the user's own words at the Mac in auto mode asked for the work. It asks before it starts only after text the talker was told (a task result, meeting words, an untrusted memory, the message being answered); after a look in an earlier turn it starts careful (ADR 14). At the Mac in auto mode a task never asks to start, and a routine asks unless the user asked for work. A careful helper is never `user_asked`, so auto mode doesn't skip its questions.
3. **Speech.** A `Speaker.utterance` has one worker. It asks `SpeechChunker` for the next piece, synthesizes it on the TTS thread and feeds it to a single open `AudioOutput` stream. Feeding doesn't block, so the next piece synthesizes while this one plays. The first piece ends at the first clause or sentence end with five or more words (or after twelve words), so Milo starts talking early but leaves the next piece time to get ready. Every later piece gets a budget: the characters the voice can synthesize while the queued audio plays, from `SynthesisPace`, a least-squares fit of a fixed cost per call plus a cost per character over the last pieces. The piece ends at the furthest sentence or clause boundary within the budget (a boundary up to 40% past it beats a cut mid-clause), never under 45 characters, because OmniVoice re-reads its 2 s voice reference on every call and shorter pieces synthesize slower than they play. With no boundary in reach it waits for the next one, up to 220 characters, rather than cut a clause in two. Each piece is trimmed to its speech and levelled to the same loudness (`speech_audio.py`): OmniVoice pads every call with about 200 ms of silence at each end and its loudness wanders by 8 dB. The pause before the next piece then follows the punctuation: 300 ms after a full stop, 160 ms after a comma, 40 ms mid-clause, and time spent waiting for a late piece counts towards it. A gap beyond the intended pause is logged as `speech gap`, and each reply's first sound as `first sound`. After the last piece a quarter second of silence and the device's own output latency play out before the stream closes, so a Bluetooth headset doesn't lose the last syllable. On Apple GPUs OmniVoice decodes its audio tokens on the GPU in 40-frame windows with 12 frames of context; one long call gives wrong audio there past 65,536 samples, and the windows match the CPU to -110 dB at twice the speed. The decoder checks itself against the CPU at warm-up and stays on the CPU if they differ. The bubble grows as each piece is fed. If synthesis fails, the text still shows and silence of about the right length plays. Barge-in calls `Voice.cancel()`, which OmniVoice honours between diffusion steps, so the TTS thread is free for the next reply within a fraction of a second.
4. **Barge-in.** Pressing the talk key while Milo thinks or speaks calls `LiveTalk.hold()`: the audio stops at once and the mic opens, but the reply keeps its place and the model keeps writing. If the user says something, `LiveTalk.interrupt()` cancels the turn and the model, and their words start the next one; side effects of the dropped reply are dropped too. If they say nothing (or the key was cancelled, as when right ⌥ types @ on a German keyboard), `resume()` goes on from the start of the sentence or clause that was cut off. A hold ends by itself after 330 s. A new typed turn interrupts at once.
   With `[chat] voice_barge_in = true` the user can also just talk over Milo. While he speaks, `BargeIn` opens the mic and lines each 16 ms block up with what the speakers played at that moment: the output says what it played and when (`PlaybackTap`) and the mic says when it heard. `EchoCanceller` (a frequency-domain NLMS filter, 128 ms long) takes Milo's echo out, and `TalkDetector` calls it the user once what is left is speech, above the room's noise floor and above the echo the canceller usually leaves, for 144 ms. Until the canceller has learned the room, the user has to be louder than Milo in the mic. Then the turn holds, the mic records until a pause, and Whisper transcribes the echo-free audio. Real words start a turn; nothing, or a transcript of Milo's own words, resumes him. The talk key always takes over. It is off by default because it hasn't been tried with real speakers and a real room yet: on Milo's real renders through simulated rooms it hears the user 114 to 136 ms after they start (274 ms for a short "Stop.") and false-triggers up to 3 times in 72 s at the loudest echo.
5. **Backchannels.** If no text of the reply has come 1.8 s into it, and still none 0.25 s later, Milo says "Hm.", "Mm.", "Hmm." or "One sec." on the reply's own stream, ahead of the answer. Text arriving in between cancels it. A conversation's first turn and short greetings never get one ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). The clips are rendered once at warm-up in his voice. One per reply, none within 30 s of the last, never the same twice in a row, never while held. `[chat] backchannels = false` turns them off.

## Quick actions

The everyday things go straight from the talker, without a helper ([ADR 29](adr/0029-quick-actions-from-the-talker.md)). A helper turn for "Dentist, Thursday at 3" took 12 to 60 s and about 60k tokens; this takes one short reply plus about 100 ms.

- **Tags.** `<event title start end? all_day? location?/>`, `<event do="move" id start end?/>`, `<event do="cancel" id/>` (id is a handle from `<today>`, or `title` with `on="YYYY-MM-DD"`), `<todo due? list?>title</todo>` (Apple Reminders, on the phone too), `<todo do="done|delete" id|title/>` (id a to-do's handle t1 from `<today>`, else a title looked for on every open list), `<note title>text</note>`, `<timer seconds|minutes|hours>title</timer>`, `<timer do="cancel" title?/>`, `<reminder do="cancel" id|title/>` (one of Milo's own, its handle r1 from `<today>`), `<draft to subject>body</draft>`, `<shortcut name>input</shortcut>`, `<music do="play|pause|next|previous"/>` and `<meeting do="start|stop|pause|resume"/>`. `ReplyParser.acts` collects them; the model says nothing about them.
- **Doing it.** Like `<open>`, an act starts the moment its tag closes, while the reply still streams (`LiveTalk._act_now`). `QuickActions` (`services/quick_actions.py`) runs each act in its own task. Calendar, Reminders and the player are the brain's own connections (`p.connections`, `services/connections.py`), the same `Calendar`, `Reminders` and `Music` ports the worker's tools use, called with `reach` (awaited when they go to the app, on a thread when they block). Where the app holds them, `core/app_connections.py` turns the ports' calls into `app_request` ops (`calendar.events`, `calendar.add_event` with `all_day`, `calendar.event` {id, at}, `calendar.update_event` {id, at, start, end}, `calendar.delete_event` {id, at}, `reminders.list`, `reminders.add`, `reminders.delete` {id}, `media.state`, `media.play`, `media.pause`, `media.next`, `media.previous`), on AppBridge in the brain and through the tool socket for the worker; the fake connections stay fake. `at` is the occurrence's start, so one of a repeating series is moved or deleted alone; when no occurrence of a repeating event starts at `at`, the app finds none rather than another one. An event named by title that only contains the words ("Dentist" for "Dentist prep") is moved or deleted only after a yes that names the title found, whatever the action's level. Notes, Mail and Shortcuts run on the brain's own `Connections` (`CONNECTIONS` from `[connections] use`) on a thread, after `AccessGate` checks the system lets Milo script the app. Timers are `loop.call_later` in the brain and ring within milliseconds; they don't survive a restart.
- **Asking.** In a conversation with outside text (task results, the screen, a `<today>` block that carried another person's line in this turn), an act asks first, as a careful action (`approve(careful=True)`), except at the Mac in auto mode (`TagPolicy.ask_acts`, ADR 35), where only ticking off a to-do on a shared list still does (`_Plan.others`). Such a `<today>` block counts like screen data for every tag in that reply: a task, a reminder, a fact or an `<open>` from it asks too. It also taints the conversation, since the model keeps the line: later turns ask like after a task result. Otherwise the kind decides: an event, a to-do, a note or the music are `change` and don't ask, a draft is `draft`, a shortcut is `shortcut` and asks every time, moving an invite is `share`, deleting your own one-off event is `trash` (Undo makes it again), deleting an invite or one of a series is `delete` and asks every time. Questions wait until the reply is over and are in the message's language (`core/words/acts.py`, keys `acts.ask.*`). Stopping or pausing notes never asks.
- **Saying it.** Once it is done, Milo says one templated line (`core/words/acts.py`, English and German, in the language `SpokenLanguage` heard, ADR 28) after the reply's own words: "Dentist, Thursday 5 November at 3 pm. It's in." A failure is a line too ("That didn't work: …"). A reply by message carries the lines instead of speaking them. It waits 10 s for them; a line that comes later (an act whose yes came late) goes to the phone as a message of its own (`QuickActions.to_phone`, `MessageService.tell`).
- **The card.** Each act emits `action_done` {kind, title, detail, when?, app?, undo?, lang} for the window's card. An event's detail is only its place: the card shows the day and the time from `when`. Music's title is Milo's line ("Paused"), with no app unless the player names one.
- **Undo.** Each change records its inverse with `Undo.done`: delete the event Milo made, move it back, make a deleted event again, delete the to-do, delete the note (into Recently Deleted), take Milo's own reminder out of `reminders.md` or write a cancelled one back, stop the timer or set a stopped one again, untick a to-do or make a deleted one again, play or pause the music again. `Undo` runs these through `QuickActions.reverse`, asking first when the user changed the event or note since (an all-day event by its title and start only: the calendar reads its end back as 23:59). A mail draft has no inverse here: its record goes to an "Undo:" helper like a task's. A shortcut and meeting notes have no Undo.
- **`<today>`.** `Today` (`services/today.py`) fetches today's and tomorrow's events, due and overdue to-dos and the player's state through the brain's connections, all three at once and the player capped at 0.25 s, when a conversation starts, after an act and when older than 5 minutes; timers come from `QuickActions`, and Milo's own open reminders from `reminders.md` are read as the block is made ("Milo's reminders:"). Without quick actions LiveTalk keeps a `Today` with no ops that carries only those reminders. It goes into a user message (never the system prompt, so the cached prompt stays the same) only when it changed since the conversation last saw it. Events get handles (e1, e2) for the conversation. Titles are inert; an event with other people is marked "invite", and an event or to-do on a subscribed or read-only calendar or list, or organized by someone else (`shared` from the app), is marked "shared".
- **Alarms.** `<alarm at/>` (text inside: what for), `<alarm do="cancel" id|title/>`, `<alarm do="stop"/>` and `<alarm do="snooze" minutes/>` go to `Alarms` (`services/alarms.py`, [ADR 38](adr/0038-weather-and-alarms.md)). They are kept in `state/alarms.json` and survive a restart. `Alarms.run` (a loop in `server.py`) checks the wall clock, at least every 30 s, because the event loop's clock stops while the computer sleeps. A ringing alarm plays a chime and one line through the speaker, again every 12 s, for at most 4 minutes; it pauses while the user speaks into the mic. A Milo key, a typed message and Stop end it (`Brain._hush`). An alarm found more than 10 minutes late doesn't ring; Milo says he missed it. Nothing rings while the computer sleeps. In `<today>` alarms get handles (a1), plus the one ringing now or just rung, so "five more minutes" can snooze it. Card kind `alarm`; Undo cancels it or sets it again.
- **Weather.** `WeatherReport` (`services/weather.py`) reads a forecast from the `[weather]` service (`Weather` port; `adapters/weather/open_meteo.py`, no key) on a thread, at most every 45 minutes, starting when the user starts talking. A failed read is logged and tried again after 10 minutes. `core/weather.lines` closes `<today>` with it: now, today and tomorrow with the chance of rain and roughly when, how much falls, the wind when it is strong, then one line per day for the rest of the week (about 100 tokens). The place is `[weather] place`, or the city of the system's time zone (`adapters/timezone.py`), so no location permission is needed. The weather doesn't count as outside text.
- **Home and Focus.** `<home device="..." do="on|off|toggle|set|open|close|lock|unlock|arm|disarm" value?/>` and `<home scene="..."/>` act on the `Home` port (`Connections.home`, `core/home.py` for devices, kinds and the forgiving name match), `<focus do="on|off" name?/>` on the `Focus` port ([ADR 37](adr/0037-home-and-focus.md)). `[home] use` picks the home (`HOMES` registry, `adapters/home/`): `home_assistant` (REST, token from `~/Milo/secrets`), `apple_home` (the user's shortcuts in a "Milo Home" folder, parsed by name), `auto` (Home Assistant when it has a url, else Apple Home where `shortcuts` exists) or `none`; fake connections bring their own. Lights, plugs, scenes, heating, fans and blinds are `change` (light: no question after outside text in auto mode); locks, garage doors and alarms are `lock`, ask_first. Undo puts each device back as the home said it was (a scene: the devices it sets), and asks again for a lock. Focus never asks. `<today>` lists the home's names by room (no states), read every 30 minutes, waited for at most 0.25 s.
- **Switches.** `[chat] quick_actions` turns all of it off; `[connections]` switches turn off single connections, `music` included.
- **Messages and calls.** `<message to>text</message>` and `<call to video? facetime?/>` ([ADR 39](adr/0039-messages-and-calls.md)). `services/people.py` turns what the user said into one person and a number or address: one said outright is used as it is; otherwise the `Contacts` port (`contacts.find` {name, relation?} in the app, CNContactStore) finds the candidates, "Mum" also through the relations on the user's own card, and an exact name beats a first name or nickname, which beats a name that only starts like it. Different names left over are a question ("Which Anna: “Anna Berg” or “Anna Kim”?"), nobody is a line. Before the first look the `AccessGate` checks `contacts`, a need the system asks about once, and says so first. Both always ask (`_Plan.always`: `confirm`, every time, in every mode and from the phone, whatever `send` or `call` is lowered to; only `never` refuses), naming the person, the number or address and the whole text. The `Messages` port is Messages through AppleScript (iMessage, else SMS through the iPhone), after `AccessGate` for Messages; the `Calls` port opens `tel:`, `facetime-audio://` or `facetime://`. The card (`message`, `call`) has no Undo.
- **Switches.** `[chat] quick_actions` turns all of it off; `[connections]` switches turn off single connections, `music`, `contacts`, `messages` and `calls` included.

## Writing where you are

"Write Anna that I'm ten minutes late", "answer this politely", "a short summary for Slack": the talker writes the text and it lands where the user's cursor is, the way dictation pastes ([ADR 33](adr/0033-milo-writes-where-you-are.md)).

- **The tag.** `<write>the text</write>`, with its line breaks, and nothing said. `ReplyParser.writes` keeps it as written and never speaks it. The rules (`writing.RULES`) put it before a `<task>` or a `<draft>`; `<draft>` is for when the user says Mail. To write about the screen ("answer this email") the talker writes only `<look/>` first and the `<write>` in its reply to the screen, so look-then-write is one turn.
- **Handing it on.** `LiveTalk._write_now` passes each closed tag to `Writer` (`services/writing.py`) while the reply still streams. `Writer` cleans it (no control characters but line breaks and tabs, no bidi, zero-width or tag characters) and sends `app_request` `text.write {text, paste}`. `paste` is false after outside text (the conversation's taint, the screen, a `<today>` with another person's line) unless the user's own words this turn asked for writing (`asks_to_write`: the writing verb leads the request or follows "can you", never a question), and for a second text in the same reply. A reply by message carries the text instead; a helper's update writes nothing.
- **Where it lands.** The app remembers the focused element when the talk key goes down (`WriteRequests.capture`, `Adapters/AXFieldProbe`). On `text.write` it reads the focus again and `Writing/PasteTarget` (pure) pastes only into that same field of that same app, never Milo's own window, a password field (or card number, or a password app) or a terminal (by bundle id, or an input labelled "terminal" like xterm.js in VS Code and T3 Code), and only into something that takes text (text with line breaks: a settable value or editable web content, so an unknown terminal's read-only text area gets none). A key press serves one paste and expires after 10 minutes, and no line break goes in at the end. The paste goes through dictation's `PasteboardInserter` (one shared instance: clipboard saved, ⌘V, clipboard back). It answers `{pasted, app, field}` or `{pasted: false, why, app}` with `why` one of `here`, `moved`, `no_field`, `secure`, `terminal`, `held`, `blocked`.
- **After.** Milo says one templated line once it is true (`core/words/writing.py`, English and German): "It's in Mail, have a look." or why it is only in his window. The window gets a `written` entry (`TranscriptEntry.written`, drawn as `WrittenBlock` with Copy), the card is `action_done` kind `written` with the first words (`app` "" when it didn't go in: "Ready to copy", a click opens the conversation), and text that stayed out gets Copy under the bubble (`MiloModel.offerCopy`, `BubbleAction.copy`).
- **Undo.** A paste records `write.remove {field, text, app}` with `Undo.done`; `Writer` puts its step in front of `Undo.reverse`. The app's `text.unwrite {field, text}` deletes the text only if the same field still has exactly it right before the caret, with nothing selected; otherwise it answers with its own words ("Press ⌘Z in Mail to take it back."), which Undo says.

## Memory

Milo remembers episodes (what happened) and facts (what is true about the user) for years. See the [design](design/memory.md) and [ADR 15](adr/0015-memory-files-and-a-rebuildable-index.md).

- **Files.** `memory/episodes/YYYY-MM.jsonl` and `memory/facts.jsonl` are append-only logs and the only truth. `memory/profile.md` is written from the facts; the user may edit it. `state/memory.sqlite` is a search index that rebuilds itself from the logs.
- **During the day.** `EpisodeTranscript` (around the transcript store) makes an episode of each user turn with Milo's answer and of each task; `RoutineEpisodes` (on `Routines.on_episode`) makes the episode of a routine run instead, a task episode named after the routine with its inputs and apps; `EpisodeEyes` of each look; `EpisodeDictations` of dictations if `[memory] dictations` is on. `<remember>` and the worker's `memory_remember` add facts. The index catches up on the memory thread in batches.
- **Each turn.** The recall runs hybrid search (FTS5 words, with German and English words for each other, and e5 vectors, merged by reciprocal rank fusion), boosts recent episodes, the current app and named people, adds the episodes of a time phrase ("yesterday", "letzte Woche"), and fits the result into `[memory] recall_tokens` (800). Outside episodes (looks, task results, meetings, outside conversations) come only when the turn asks about the past or about outside text (`about_the_past`: what someone said, wrote or sent, mail, messages, results, "remember", "yesterday" and German forms), or when it comes from the phone. Then they come marked as data and taint the conversation (ADR 10). Small talk at the Mac recalls only facts and trusted episodes, so it stays trusted ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). No model call.
- **At night.** `SleepRunner` consolidates each finished day with one worker call: better summaries, new, changed and retired facts, and a journal section. Every change is a log line; `python -m milo.memory.consolidate --undo <run>` takes a night back.
- **The user's view.** "What Milo knows…" in the menu bar lists the facts by topic with Edit and Forget. The worker has `memory_search`, `memory_remember` and `memory_forget` in the `milo` MCP server; the latter two ask the user first.

## Helpers

The chat model, the talker, has no tools and never waits for work. Opening something is not work: `<open>` opens it at once without a helper (see A user turn). Work that needs files, research, the user's apps or the screen comes out of a reply as a `<task>`, and `services/orchestrator.py` hands it to a helper: one run of the agent harness (`[harness]`, Codex by default) in its own process and its own session, working in `~/Milo/work` under `AGENTS.md`, with a sandbox that can't write Milo's control files (ADR 20). See [ADR 11](adr/0011-helpers-and-the-orchestrator.md).

- **At once and in turn.** Up to `[harness] max_helpers` (3) helpers work at the same time; more wait as queued. Helpers with `screen="yes"` take turns on the screen harness (with the milo-mac tools). The rest run on a second harness instance without them. A background helper that answers `NEEDS_SCREEN` is queued again for the screen.
- **Only what the task needs.** `core/task_scope.scope_for` reads the task's words for the connections it names (calendar, mail, files, …). The connection server serves only those (`MILO_TOOLS`) plus Milo's own tools; the first prompt names every tool the helper has with its arguments (`connect/brief.py`), plus their rules once and a fixed safety paragraph, so the worker calls them without listing them first; Codex gets AGENTS.md trimmed to the task's sections with each new session (`developer_instructions`). A known scope off the screen runs on `[harness.codex] light_model` (`gpt-6-luna`). An unclear task gets everything; a helper short of a tool answers `NEEDS_TOOLS` and runs again with all. A calendar read went from 12.6 s and 63k tokens to 7.9 s and 29k (6.4 s on the light model). See [ADR 32](adr/0032-helpers-get-only-what-their-task-needs.md).
- **Milo's tools only.** Both harness instances run without the user's own setup: Codex in a home of Milo's own (`~/Milo/.codex`, rewritten before every turn, the login linked from the user's), Claude Code without user settings, skills and other MCP servers. See [ADR 13](adr/0013-a-worker-with-milos-tools-only.md).
- **The board.** Before every user message the talker gets a `<helpers>` block from `services/helpers.py`: status, time, step count and the last steps in plain kind words and installed app names, never file names, commands or page text. So it can answer "how far are you?" without the conversation counting as tainted.
- **Steer and stop.** `<steer>` stops the helper's turn and resumes its session with the change; without a session the task starts over with the change written in. `<stop>`, or `stop_helper` from the Stop button in the Milo window, kills the worker's whole process tree. A steer asks first once the conversation is tainted, a stop never does.
- **Waiting for an answer.** A helper whose question outlasts its worker's turn parks (`Orchestrator.park`): the board and its bird show "waiting for your answer" (`needs_you`), the supervisor waits for the answer, and a yes continues the session with `task_runner.answered_prompt`; the same question from that helper in the next turn counts as the yes, once, never for money. A no ends it with "You said no, so I left it.", and Stop takes the question away ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)).
- **Careful helpers.** A task the user asks for in a conversation that has seen the screen starts at once, but its helper runs careful (`Helper.careful`): Approvals asks before its `change` actions too, and HandsService asks once per app before the first change there. The flag is per helper: `TaskRunner` passes it to `hands.begin`, and `HelperQuestions` passes it to `Approvals.approve` for the connection tools (any careful helper at work counts when the tool socket can't tell which one asks). In auto mode (ADR 22) a task from the reply to a look starts without that question when the user's words in that turn asked for work, and its helper is `user_asked`. A task or steer the chat model starts on its own in reply to screen data or after reading untrusted text asks first, in one sentence of at most 80 characters (`reply_effects.task_question`); the whole task shows under it in the Milo window. See [ADR 14](adr/0014-scripts-milo-writes-and-short-questions.md).
- **Updates.** `services/updates.py` finds milestones with rules over step kinds and titles and tells the user as `[chat] updates` says: `quiet`, `bubble` (a short note) or `chatty` (the talker says it, at most every 45 s). A task asked for by voice that is still at work after 8 s gets one spoken line in the user's language from what it is doing ("Opening Microsoft Excel now…", `updates.progress_line`, no model call), unless `quiet`; then Milo stays quiet until the result or a question (ADR 32). `LiveSettings` re-reads `config.toml` when it changed, at most every 2 s, so `updates` and `max_helpers` apply without a restart.
- **Results.** When a helper finishes, Milo speaks its `say` and the next chat message carries the result. A result that finishes during a live turn waits up to 30 s for the turn to end, then shows silently. Heartbeat nudges wait the same way, and a silent bubble never cuts off speech.
- **The app.** The `helpers` event lists every active helper and, for 8 s, the ones that just ended (step changes coalesced to every 0.25 s). `step` is what the helper does now in plain words (at most 64 characters, the title the Milo window shows); for the screen helper it follows the Mac tools' steps too (`ScreenSteps`), and its entry has `"screen": true`, so the caption under the working outline can read `step` from that entry (it reads the `hands_` activity steps today, which carry the same titles, ADR 30). The overlay shows a small bird per helper next to Milo; a click opens its task page in the Milo window. Today lists the helpers at work with Stop, and each task is a card in its conversation.

Task results reach the chat model as `<task_result>` blocks with `<` and `>` escaped, and the reply rules say they are data. Once a result is in the conversation, LiveTalk asks before it acts on any later tag in it, until the conversation resets. See [ADR 10](adr/0010-untrusted-results-and-a-private-log.md).

## Routines

A routine is a recipe in words that a helper follows again: `~/Milo/routines/<slug>.md`, Markdown with front matter (`name`, `description`, `inputs`, `schedule`, `apps`, `paused`, `last_run`, `version`) and a body with Goal, Steps with `Check:` lines, and Ask first. `services/routines.py` owns them. See [ADR 16](adr/0016-routines.md).

- **Tags.** The talker writes `<routine do="create|save|change|run|schedule|rename|pause|resume|delete" name="...">`. The system prompt lists the routines by name and schedule, with names inert like task results. Create never asks (the draft is looked at before it counts); the others follow the task rule of a tainted conversation.
- **Create.** A careful helper writes a draft to `state/routine-drafts/` from the last finished helper's task, steps and result. The brain normalizes it and sends it in the `routines` event; the window's draft card shows the steps, inputs and apps, or the whole file, with Save and Change it (`routine_draft_answer`).
- **Run.** A helper gets the recipe and the inputs (`month: October`, a bare value for a single input, or the defaults). A recipe changed since it was saved, or a schedule set outside Milo, asks before it runs. `last_run` and `state/routine-runs.jsonl` record each run.
- **Schedules.** `HeartbeatRunner.on_tick` calls `Routines.tick`, which costs no model call. Missed runs coalesce into one, run at wake within `[routines] grace_hours` and are reported after it. `[routines] max_runs_per_day` caps scheduled runs.
- **Tasks that repeat.** `Orchestrator.on_done` calls `Routines.seen`, which keeps the shape of each finished task (`core/task_patterns.py`) for 45 days and offers, once per kind, to keep the third one alike as a routine.
- **The window.** A Routines section above the conversation lists them with their schedule, next and last run, Run now and a menu for pause, resume and delete (`routine`).

## Looking and computer use

See [ADR 6](adr/0006-looking-at-the-screen.md) and [ADR 7](adr/0007-computer-use-through-the-brain.md).

- **Looking.** The chat model writes `<look/>` when it needs to see the screen. LiveTalk asks through the `ScreenEyes` port (`AppEyes` sends `look_request`), the app answers `look_result` with the front window's text and a screenshot path, and LiveTalk sends both to the model as a second message with an image block. `looking` turns the eye badge next to Milo on and off. "What's this?" (the shortcut or the menu item) sends `whats_this` with a capture, and the brain starts a turn with it. Screen text sits between `<screen_data>` markers (`services/screen.py`), and a task from a conversation that has seen it runs careful (see Delegated tasks).
- **Computer use.** Workers get the milo-mac tools (`core/hands.py`) through `AdapterContext.mac_tools`, which compose.py fills when `[hands] enabled`. Codex and Claude start `python -m milo.mcp_server`, next to the app connections server, and it sends each call to `~/Milo/run/hands.sock`. `HandsService` validates it, asks the app to describe the target, classifies it with `services/risk.py`, asks through the `Confirmer` port (`Approvals`, see below) when needed, logs a step, and then has the app run it (`hands_request`, `hands_result`). It only answers while a screen helper runs, and only one does at a time.
- **Background delivery.** `MacHands` works on apps without the real cursor or keyboard where macOS allows it, deciding the route per app family with the pure planner `Screen/Delivery`: `AXPress` for buttons, `AXFocused` plus a caret for a click into a field, `AXSelectedText` (read back) for typing, `AXShowMenu` for a right-click, the scroll bar's value for scrolling. What can't be done that way (a plain keystroke, a double-click, web content, Office documents) returns `HandsFailure(borrow:)`; `HandsService` asks "Can I borrow your mouse for a moment?" through the `Confirmer`, and on a yes sends `hands_borrow`. The app lends that one device on a 15 s sliding clock and warps the real pointer back afterwards. See [ADR 12](adr/0012-background-delivery.md).
- **Opening and aiming.** `open_url` (a web page, in the browser the user named) and `open_app` come first in the worker's routes, never keys or scripts. The app opens through Launch Services (`/usr/bin/open`), which activates even while Milo isn't the active app and asks a running app without windows for one, then waits at most 2 s until the app is in front with a window and answers `front`. `MacHands` runs the three open tools on a queue of their own, so the talker's `<open>` never waits behind a helper's script. `click`, `type` and `key` take `app`, else the app the task last opened or named, else they are refused. Before describing the target, `HandsService._aim` sends `focus_app`, and the app brings that app to the front (bounded at 2 s). If the target is then another app, the action is refused with words for the worker, before any question. Any acting tool whose target is Milo's own window (`describe` says `milo`) is refused the same way, so no question and no Allow always ever names Milo, and the app refuses to press, fill in or type into its own elements (`MacHands.notMilo`). `OpenGuard` (pure, in `Screen/`) refuses addresses that aren't http or https and files that would run code; a file always opens in its own app. A careful helper's `open_url` asks first. A helper's first prompt names its tools with their arguments, so a Codex worker doesn't list them all (each description came back with the server's instructions in front, about 11,600 tokens that every later step resent); the servers send no instructions any more, the prompt carries them once (ADR 32). See [ADR 28](adr/0028-open-at-once-and-answer-in-the-users-language.md).
- **Scripts Milo writes.** `sheet_write`, `sheet_read` (Excel, Numbers), `write_document` (TextEdit, Pages) and `ax_find` are composed in the brain: `services/sheets.py` and `services/documents.py` turn plain arguments into AppleScript with every value as an escaped literal, and run it through the app's `run_applescript` action, which works in the background. They need no question unless `sheet_write` would replace filled cells. `sheet_write` also colours (`fill`, `font_color`: a range, `header` or `sheet`, the used range, and a colour name or `#RRGGBB`); without `rows` it only formats, so "make the header blue" is one call (ADR 32). The tool descriptions put them first, then `run_applescript` (always asks), then the accessibility tree, then screenshots. See [ADR 14](adr/0014-scripts-milo-writes-and-short-questions.md).
- **On screen.** Milo's own cursor in his theme's colours (`AppKit/CursorOverlay`, a click-through overlay, never the system cursor) glides to each spot before the action, ripples on a click and shows a caret while typing. The window he works in gets a soft outline with a "Milo is working here" tag (`AppKit/WorkingOutline`, `MiloModel.workingWindow`), followed by `Adapters/MacWindowWatcher`. The outline sits just above that window in the window order (`workingWindowNumber`, the window server's number for it), so windows in front of it cover it too, and it hides while the window is minimized, its app hidden or it is on another space. Every click goes through it, and it stays under Milo's own panel: it once sat above him and swallowed the clicks on his Yes and Allow. Milo flies to its corner and perches there (`FlightDriver`). The whole-screen frame (`AppKit/WorkingFrame`) shows only while the real mouse or keyboard are borrowed. `describe` returns the target's `window` and `pid` for the outline. Scripts and the sheet and document tools have no spot to describe: before the first one in an app the brain sends `show_app` with that app (`HandsService._show`, once per app per task), and the app outlines its main window and brings it forward the same way (`WindowWatcher.mainWindow`). With `[hands] show_window` on (the default, a switch in Settings) that window comes to the front once when Milo starts in an app (`WindowWatcher.bringForward`: the window is raised and its app activated), so the user sees the work; if they click away, he doesn't pull it back until he moves to another app. Off, he works behind the user's windows and only the outline shows where.
- **The step under the outline.** `MiloModel.workingStep` is what his hands do now, in plain words: the newest running `activity` step whose id starts with `hands_` (from `HandsService`), never the worker's own steps. It clears when the hands stop. `WorkingOutline` shows it as a small pill on the window's bottom edge (`WorkingCaption`). See [ADR 30](adr/0030-cards-for-what-milo-did.md).
- **Stopping.** `Screen/ScreenController` watches real input during a session through `UserInputSource`. `TakeoverDetector` is pure and has two modes: in `background` the user's own mouse and keyboard never stop Milo (that's the point), only `esc` or the Stop button by Milo does; while a device is `borrowed` any real touch stops him, as before. Input doesn't count while a question waits (`confirm` until `confirm_done`). On a stop the app sends `hands_stop` and the brain fails every later call in that task.
- **The system's permissions.** `services/access.py` (`AccessGate`) checks what the system lets Milo do before an action needs it, in the neutral words of `core/access.py`: `control` an app, work other apps' windows (`ui`), see the `screen`; `yes`, `no`, `ask`, `unknown`. The app answers `access.check`, `access.request` and `access.places` (`Access/AccessRequests`, `Adapters/MacAppAccess`). Before macOS's first "Milo wants access to control …" Milo says one line (`access` event, state `ask`) and the task shows "Asking to use …". A no shows Fix it under the bubble, and the worker hears it plainly. An allowed app shows nothing. The check comes after Milo's own yes, so an action he refuses never starts an app or a prompt. `MacHands` won't run a script that makes a sandboxed app save outside its own places (`SandboxGuard`), which would block it on "Grant File Access". The menu bar and the permissions window list the apps macOS was asked about (`ControlledApps`). See [ADR 25](adr/0025-the-systems-permissions-before-milo-needs-them.md).
- **Stop by Milo.** While he talks, thinks, works on screen or has a helper at work (`MiloModel.canStop`), a small Stop button shows at his side, by his left wing (`StopByMilo`). It sits inside the square his panel keeps for dragging him, so the panel hands a press there to the button instead (`DraggableHostingView.isControl`, `OverlayPanel.stopCenter`). It stops the screen work in the app at once (`hands_stop`) and sends `stop_all`: the brain answers the question waiting no, stops every helper and the hands, and cuts off what he is saying or thinking.

## App connections

The worker reaches the user's apps through one MCP stdio server, `python -m milo.connect`, which `compose.py` passes to the harness as a `ToolServer`: Claude Code gets `--mcp-config state/mcp-servers.json --strict-mcp-config --allowedTools mcp__milo-mac mcp__milo` (milo-mac only when `[hands] enabled`), Codex gets `-c mcp_servers.milo.*` and `-c mcp_servers.milo-mac.*`. The server's 20 tools sit on the connection ports in `milo.core.ports` (`Calendar`, `Reminders`, `Mail`, `Notes`, `Shortcuts`, `Files`). `[connections] use` picks the adapter set (`CONNECTIONS` registry): `mac` or `fake`. Each connection has its own switch.

```
worker CLI ──stdio──▶ milo.connect ──run/tools.sock──▶ brain ──brain.sock──▶ Milo.app (EventKit)
                         │                               │
                         ├─ AppleScript (Mail, Notes)    └─ Approvals: bubble, window, voice
                         ├─ shortcuts CLI
                         └─ mdfind, textutil, PDFKit
```

- **Before any change** the server asks the brain over `run/tools.sock` (0600, peer UID checked, one JSON object per line, `id` echoed): `{"op": "approve", "kind": "send", "summary": "Write a draft to Anna?", "app": "Mail"}` (`app` optional: the app a change happens in, so an Allow can cover the next one) returns `{"ok": true, "result": {"allowed": true, "level": "ask_first", "answer": "yes"}}`. `{"op": "confirm", "summary": ...}` returns `{"result": {"yes": bool}}`. If the brain can't be reached, reads go ahead and everything else is refused.
- **Calendar and Reminders** run in the app: `{"op": "app", "name": "calendar.add_event", "args": {...}}` on the tool socket. The brain checks the connection switch, asks if the level says so, then sends `app_request` to the app and waits up to 90 s for `app_response`. Ops: `calendar.events` (start, end, query), `calendar.add_event` (title, start, end, location, notes, calendar, all_day), `calendar.event` (id, at), `calendar.update_event` (id, at, start, end), `calendar.delete_event` (id, at; `delete`, asks every time from the tool socket), `reminders.list` (query, include_done), `reminders.add` (title, due, notes, list), `reminders.complete` (id, done: false unticks it), `reminders.delete` (id; `delete`). The talker's quick actions also send `media.*` (Quick actions above). Times are local, `2026-11-05T15:00`.
- **The system's permission.** Before its first script in Mail or Notes, the server asks the brain `{"op": "access", "app": "Mail"}` (only Mail and Notes). The brain says what is coming if macOS is about to ask, and a no comes back as plain words with Fix it in the bubble (ADR 25).
- **Kinds.** Reading is `read`, a mail draft is `draft`, passing an email on is `share`, a new event, reminder or note is `change`, running a shortcut is `shortcut`. See [ADR 8](adr/0008-app-connections-as-an-mcp-server.md) and [ADR 9](adr/0009-approvals-and-action-levels.md).
- **Unknown arguments** are refused, and a tool whose question needs facts (whose email is being passed on) looks them up with a read before asking.
- **Step titles** for the window come from `milo.core.wording.title(tool, args)`, so a task shows "Looking in your calendar" and not `mcp__milo__calendar_events`.

## Approvals

`Approvals` owns the one open question. `approve(kind, summary)` looks up the level in `[approvals.levels]`: `read` and `change` go ahead, `never` is refused, `ask_first` asks. `trash` (to the Trash or Recently Deleted) is a change that asks only in "Every step" mode; `buy` and `money` are `ask_first` with `confirm.money` set: no Allow always, only a click on Yes counts (`answer` refuses a spoken, typed or phone yes), and while the owner is away the question isn't asked at all ([ADR 23](adr/0023-stop-for-what-cant-be-undone.md)). Asking sends `confirm` (the bubble and the window show Yes and No), speaks the question unless a turn is running, and waits for `confirm_answer`, a short spoken or typed yes or no while the bubble still shows the question, or `[approvals] timeout_s`, which counts as no when it is above 0. By default (0) a question stays open until it is answered, and Milo says it once more after `[approvals] reask_s` (20 s) when nobody is talking. A helper's question keeps its tool call waiting until 20 s before the harness would end the worker's turn (at most 200 s); then it parks: the worker is told to end its turn and say it waits, the helper shows "waiting for your answer", and a yes continues its session, a no ends it ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). `confirm_done` tells the app it is over. Computer use asks through the same flow with `confirm(summary, undo=, money=)`; its own classifier (`risk.classify`: `OK`, `UNDO`, `ASK`, `MONEY`, `NEVER`) decides when, so the levels don't loosen it. `undo` questions only ask in "Every step" mode. `approve(kind, summary, careful=True)`, for a careful helper (see Delegated tasks), asks before `change` actions as well.

**One question per piece of work** ([ADR 22](adr/0022-one-question-per-piece-of-work.md)). A question about work in an app carries a `Scope` (its apps and the helper that asks): replacing filled cells, a script for one app that reaches nothing outside its document (`risk.coverable_script`, `hands.script_apps`), borrowing the mouse there, a careful helper's first change and its connection-tool changes. `Permits` decides in the question's lock whether an earlier answer covers it. With `[approvals] ask = "auto"` (the default since ADR 23) a helper with `user_asked` needs no question at all, and other helpers behave as in `"task"`. With `"task"` Allow covers the scope until the helper ends (`Orchestrator.on_done` calls `end`). With `"step"` it covers only that step. Allow always (`confirm.always`, `confirm_answer.always`) adds the app to `[approvals] allowed_apps` through `Settings.keep`, and covers it in every mode. Questions without a scope (send, share, delete for good, Don't Save, replacing a file, buy and money, shortcut, code, settings, files, unnamed clicks) ask every time, and `never` and risk's never-rules refuse before any of this. Only the button means always: a spoken, typed or phone yes allows this time. A question with its own buttons (`Approvals.choose`, `confirm.choices`, like the meeting question's) shows only those: no Allow always, no scope and no money styling. Its answer comes back as `confirm_answer.choice`, which wins over `yes` and `always`; its "always" is the asker's own, saved by the asker (Meetings into `[meetings] always`), never `allowed_apps`.

## Cards for what Milo did

`action_done` `{kind, title, detail, when, app, undo, lang}` says Milo just did something small: an event, a to-do, a reminder, a note, a timer, a draft, a shortcut, music, a page opened, text Milo wrote ([ADR 30](adr/0030-cards-for-what-milo-did.md)). LiveTalk sends it for `<reminder>`, `Opener` for what `<open>` opened (the address in `detail`). The instant actions send it for the rest. `lang` is the language Milo said it in; the card's own words ("Today", "In your calendar") follow it, else the system's (`DoneCardText`, English and German). In the app, `DoneCards` (owned by `MiloModel`) keeps up to three cards, each for 4 s and longer while the pointer is on them. `Views/DoneCardViews` draws them left of Milo as a deck that fans out under the pointer: a picture of the thing (calendar page, checkbox, timer ring, note sheet, envelope, app icon), the title and when, a check that draws itself in, and Undo when the action has a task (`undo_task`). A click opens the item where it lives (`DonePlace`, carried out by `Adapters/MacItemOpener`): the event in Calendar, the to-do in Reminders, Milo's own reminders on Today, a page Milo opened (only from `detail`, never a title, which may be a file's name). The cards report their frame (`DoneCards.area`), so the panel's `isControl` hands a press there to them, as for Stop.

## Undo

`Undo` (`services/undo.py`, [ADR 26](adr/0026-undo-what-a-task-did.md)) gives every task that changed something a way back. `HandsService` calls `before_change` right before a Mac action that may change something: for Excel, `snapshots.py` has Excel copy the workbook's sheets to `milo-undo-<task>-<n>.xlsx` in its own container folder (alerts and screen updating off, a timeout, no other paths), once per workbook per task; every change is recorded. Workers keep files with the `undo_point` tool (copied on a thread, like the hashes and putting files back: a file may be 200 MB) and note what can't be copied with `undo_note` (through `ToolRequests`, by the task id in their first prompt). `Orchestrator.on_done` calls `finished`, which marks the record ready and stores fingerprints and hashes. `undo` (from `undo_task`, a bubble's Undo or the talker's `<undo/>` tag) asks only when the document changed since, restores copies and files, hands the rest to an "Undo:" helper, and says what it did. When what is left only opened windows or tabs (`open_app`, `open_url`, `core/hands.only_opens`), or is notes with no recorded change, no helper starts: Milo says in one line that there is nothing to undo ([ADR 31](adr/0031-talk-as-naturally-as-dictation.md)). `FileUndoShelf` (`memory/undo_shelf.py`) keeps `Workspace.undo_dir/<task>/record.json` and `files/`; records expire after a day or beyond the last 20 tasks. It reads the records once, at its first use, and keeps them in memory, writing through. At start-up `Undo.recover` makes a record a crash left "open" ready (careful, or dropped if it changed nothing) and one left "undoing" ready again, so neither keeps its copies or a spinner for good. `undo_points` tells the app which tasks can be undone. A quick action's record (`Undo.done`) carries its own `reverse` steps, which `QuickActions.reverse` runs, newest first; a step done stays done, so a second try goes on where the first stopped.

## Milo by message

The owner reaches Milo from their phone through a chat app (`[messages]`, off by default). See [ADR 17](adr/0017-milo-by-message.md) and the [setup guide](setup/messages.md).

```
phone ──Telegram──▶ api.telegram.org ◀──HTTPS long poll── brain: TelegramChannel ──▶ MessageService
                                                                                       │
             pairing code ◀── bubble and window on the Mac ◀────────────────────────────┤
             LiveTalk.message (text turn, same conversation) ◀──────────────────────────┤
             Approvals questions while away ──▶ Yes/No buttons in the chat ─────────────┤
             helpers started from the phone ──▶ milestones and results in the chat ─────┤
             worker's send_to_phone ──tools.sock──▶ check, ask "share", send the bytes ─┘
```

- **Channels** (`CHANNELS` registry, `core/ports.Channel`) only move messages. Telegram uses the Bot API over HTTPS with the standard library, so nothing on the Mac listens for the network. The token comes from `~/Milo/secrets/telegram-token` (0600, never logged). Every secret file (this token, the ElevenLabs key) is read through `core/secrets.read_secret`: a plain file the user owns, made 0600 in a 0700 folder if it was more open, links and other users' files refused. iMessage reads chat.db read-only (Full Disk Access) and sends with AppleScript to the owner's own handle only.
- **Pairing** (`services/pairing.py`): the first message from an unknown private chat makes a 6-digit code that shows on the Mac only; sending it back makes that chat the owner (`state/messages.json`, 0600). Codes are tied to their chat, last 10 minutes and 5 tries. After pairing everything but the owner's private chat is dropped and logged without its text.
- **Turns.** `LiveTalk.message` runs a text turn on the live model: same persona, memory and helpers, no speech, no looking. Forwarded, quoted and long (pasted) text goes in as escaped `<forwarded>`, `<quoted>`, `<pasted>` data and makes later tags ask first.
- **Questions.** `Approvals.relays` holds the MessageService. While the Mac has been idle for `away_after_min`, a question goes to the chat and only the chat may answer (`Relayed.only`); while the owner writes from the phone and the Mac is in use, both may.
- **Files.** The connections server lists `send_to_phone` when messages are on. `ToolRequests` asks `services/sharing.py` whether the file may go (no private folders, case-insensitive, links resolved, at most `max_file_mb`), asks `share`, then sends the bytes read through one descriptor opened without following links, if it is still the same file.
- **Safety while away.** `services/settings_guard.py` puts `config.toml`, `state/messages.json` and `secrets/` back if they change while the owner is away (Milo's own saves excepted). `/pause` works from the phone; resuming, pairing and disconnecting only at the Mac (the menu sends `remote_pause` and `remote_forget`).
- **Morning brief** (`services/brief.py`, `brief_at`): today's events and Apple Reminders from the talker's day (`Today.current`, read again only when older than 5 minutes, so the brief and `<today>` don't fetch the calendar twice), `reminders.md`, helpers at work. Templates only, zero tokens, on the heartbeat's tick (`HeartbeatRunner.on_tick`).

## Logs

`logs/brain.log` rotates at `[logging] max_mb` and keeps `keep` old files. It holds sizes and timings, never what the user said, Milo's replies or file contents: services log `milo.core.logtext.private(text)`, which is `<42 chars>` unless `[logging] content = true`. `logs/connect.log` is the MCP server's.

## The Milo window

The window has the conversations down its left side and a page beside them: Today, a conversation, or a task. Clicking the character or "Open conversation" in the menu bar item opens it; a second click or the close button hides it. macOS keeps its frame. The design is in [design/conversations.md](design/conversations.md) and [ADR 19](adr/0019-conversations-that-split-on-their-own.md).

- **Conversations.** `services/transcript.py` holds the conversation going on and asks `core.conversations.split()` at every user turn whether it starts a new one: after `[chat] conversation_idle_reset_s` of quiet, when the user asks for one (⌘N), after a 2-minute pause with no word in common with the last two turns, or when a turn comes from another channel. It never splits on an answer or while Milo waits for one. Each conversation is a JSONL file under `state/conversations/`; its id is `c-` and its first entry's id. Routine runs and meeting notes get conversations of their own.
- **Titles.** The first user turn gives a title from its words at once (`title_from`). On the reply to the first turn LiveTalk appends `[name this conversation]`, and Milo's `<title>` tag, taken out of the reply stream, replaces it. A name the user gives (double-click the title) wins over both.
- **Picking up.** Typing in an older conversation sends `text` with its `conversation`. The brain makes it the current one again and gives the chat model an `<earlier_conversation>` recap of its last lines within `[chat] recap_tokens` (600). The recap is untrusted when that conversation saw outside text or a task's result (LiveTalk's `carries_outside`, memory on or off), and always for meeting notes and routine runs.
- **Events.** On connect and when the window opens the brain sends `conversations` (the headers, the current id, whether older ones exist), `history` (the current conversation's entries) and `reminders` (open ones due before the end of tomorrow). `entry`, `reply_delta` and `activity` stream as before, each entry with its `conversation`. `open_conversation` answers with `conversation` (the header and its entries), `search_conversations` with `search_results`. None of them call a model.
- **Activity.** `Harness.reply` takes an optional `on_step` callback. The worker adapters read the CLI's stdout line by line while it runs: `codex exec --json` reports `item.started`/`item.completed` for `command_execution`, `file_change`, `mcp_tool_call` and `web_search` (reasoning, messages and todo lists are skipped), and `claude -p --output-format stream-json --verbose` reports `tool_use` blocks with their `tool_result`. `adapters/harness/_activity.py` turns each into a `Step` with a plain title ("Reading your Downloads folder", "Opening Microsoft Excel", "Searching the web for ...") and keeps the raw command or tool payload as `detail`, shown only when the row is expanded. Callers without a callback get the same `Reply` as before.
- **Tasks.** In a conversation a task is one card: its title, its state and its current step. The card opens the task's page with the result, the files it names that exist (`files`, checked when it finishes) and every step.
- **Today.** What waits for the user (Milo's question, a recipe draft), what Milo is working on, today's reminders, what got done today and the last conversation to pick up.
- **Questions.** While Milo waits for a yes or no, the bubble shows the question with Yes and No buttons and stays up, and a bar above the text field and the Today page show it too.
- **Typing.** The text field sends `text`. The window's "speak replies" toggle (off by default, kept in UserDefaults) adds `"speak": false`, and Milo then answers in the bubble and the window without audio.
- **Keys.** ⌘1 Today, ⌘2 Usage, ⌘N a new conversation, ⌘F search, ⌘[ back, ⌥⌘↑ and ⌥⌘↓ the conversation above or below, ⌘L the text field, ⌘0 the sidebar in a window narrower than 600 pt, Esc clears the search or leaves a task.

## Usage

The Usage page in the Milo window (⌘2, under Today in the sidebar) shows tokens and dictations per day over 7, 30 or 90 days, where the tokens went (talking, tasks, memory upkeep), which apps got the dictated words, and the accounts Milo uses. It costs no model call.

- **Protocol.** The app sends `get_usage {span}` when the page opens and when the range changes. The brain answers with `usage {span, today, since, daily, sources, apps, accounts}`: every day of the range (calls, input tokens with the cached ones inside, cached, output, dictations, words), tokens per `source`, the top 6 apps by words, and one row per service `{service, uses, state, plan, who, detail}`. No dictated text leaves the brain, only counts and app names. The app keeps only the answer for the range it shows.
- **Reading.** `memory.usage_log.JsonlUsageHistory` reads `state/usage.jsonl` and `dictation-history.jsonl` back, skipping lines before the range by their date prefix before parsing; `core.usage.summarize` totals them. Both files only grow, one short line per call or dictation, so a year of heavy use is a few milliseconds of reading. With `[dictation] keep_history = false` there are no dictation counts.
- **Accounts.** `adapters.accounts.CliAccounts` asks the services `config.toml` picks: `claude auth status` (signed in, email, plan), `codex login status` (how it is signed in; Codex doesn't say the plan), and ElevenLabs' `/v1/user/subscription` with the key in a header (plan and credits, but only for a key with the `user_read` permission; otherwise the row says so). Local parts show as "This Mac". Each check has a 5 s limit, and a failure becomes a row that says why.
- **Never in the way.** `UsageService` answers on a task of its own and reads on worker threads, so a key press right after opening the page isn't held up. The page gets the numbers at once; the account check, reused for 10 minutes, follows in a second `usage`.

## Settings

The Settings window changes a few keys of `~/Milo/config.toml` through the brain; the app stores nothing.

- **Protocol.** The app sends `get_settings` when the window opens and `set_setting {section, key, value}` for each change, from the window or the menu's "Dictation style". The brain sends `settings` on connect and answers both with `settings {settings, restart, error}`: one row per setting with `value`, its `options` and their plain `labels` (both empty for a switch), and `live`. `restart` is true while a saved change waits for one; `error` says in plain words why the last change wasn't saved.
- **What can change.** `settings.SETTINGS` lists them: `[chat] updates`, `[dictation] stream`, `[dictation] learn`, `[ui] dictate_key`, `talk_key`, `whats_this_key`, `[ui] voice`, `[ui] hide_after_s`, `[approvals] ask` and `[approvals] allowed_apps`. Anything else is refused, and so is a list of allowed apps that adds one: only Allow always adds them. While `ask` is `"auto"`, the default, the menu says so and has a "Turn off auto mode" item; the menu bar icon has no badge for it.
- **Saving.** `config_file.TomlConfigFile`, the brain's only writer of config.toml, edits the file with tomlkit, so comments, order and blank lines stay, and a comment at the end of the changed line keeps its column. It loads the edited text with `Config` first and writes nothing if it fails (a clash of keys, a wrong type, an already broken file); the write goes to a temporary file that replaces config.toml.
- **Applying.** `compose.py` hands `Settings` one function per key that can change live: the look and the keys re-send `ui_config` (and later connects send the new one), `voice` sets `Speaker.silent` (replies still show piece by piece at speaking pace, without audio), `stream` sets `Listening.live_mode` for the next recording, `[chat] updates` goes to `LiveSettings` at once (the helpers' updates; it would otherwise notice the changed file within 2 s), `[approvals] ask` and `allowed_apps` go to `Permits`, and `[hands] show_window` and `[ui] hide_after_s` need nothing in the brain: the app reads them from the next `settings` report. Every setting in the window applies live today; a key without a function would wait for a restart, and the window would then show a Restart Milo button, which restarts the brain.

## The setup window

`SetupWindow` opens by itself at launch when the microphone, Accessibility or Screen Recording is missing, and from the menu bar as "Check permissions…". Calendars, Reminders and Mail and Notes (Automation, checked against Mail) are optional rows.

- **Checks.** `SetupModel` reads every permission through the `PermissionSource` port (`SystemPermissions` in the app, `FakePermissions` in tests) once a second, only while the window is open, so a tick appears as soon as the switch flips.
- **Granting.** The row's button first puts Milo in that permission's list (`register`: `AXIsProcessTrustedWithOptions` with the prompt, `CGRequestScreenCaptureAccess`, `AVCaptureDevice.requestAccess`, EventKit's request, an Apple Event question to Mail). Where macOS hasn't asked yet and asks in a dialog, that's all; otherwise it then opens the exact page (`x-apple.systempreferences:com.apple.settings.PrivacySecurity.extension?Privacy_…`). For Accessibility and Screen Recording a small floating panel shows Milo as a tile to drag into the list.
- **Stale entries.** After a rebuild macOS can show Milo switched on while the check says no. A permission that was granted before (remembered in UserDefaults) or is still off 8 s after its page opened gets a Fix it button: `tccutil reset Accessibility|ScreenCapture <Milo's bundle id>` for Milo's own entry only, then register and open the page again.
- **Screen Recording** only counts after a restart, so once its page was opened the row offers Restart Milo, which relaunches the app.
- **Scenes.** Each row plays a short loop of what Milo does with the permission, drawn with Milo himself (`Views/SetupScenes.swift`), only while the window is open; with Reduce Motion each shows its last step still.

## The overlay, moment to moment

The overlay reacts to the keys before the brain does. `MiloController` shows each push-to-talk output on the model in the same call that sends it (`MiloModel.press`, `hold`, `release`, `cancelPress`), so the view commits within about 2 ms of the key (`ResponseLatencyTests`), a round trip and the 80 ms `showAfter` ahead of the brain's own state. One capsule over Milo (`Views/VoiceCapsule`, its look picked by `VoicePhase.of`) changes shape from step to step: a small light at key down (only a light, since it may still be a tap or a right-Option shortcut), the level meter and the words so far once the key has been down 80 ms, "Got it" for 0.6 s at key up, dots while the words are worked out and while he thinks ("Still on it" after 6 s), and "Pasted" for 1.4 s after dictation lands. It springs in with the theme's motion and leaves in 0.12 s.

The bubble (`Views/BubbleView`) holds his answer, a question with Yes and No, or a note with a button that fixes what it is about (`BubbleAction`, "Fix it" opens the permissions window). It hugs short text. While he speaks, `SpeechReveal` lays out each piece the brain sends, hidden, and shows its words at the speed he talks, learned from how long each piece took, so lines never reflow. The mic and voice level live in their own `MiloModel.live`, which only the figure and the meter watch.

**Leaving the screen.** After `[ui] hide_after_s` seconds (15 by default; Settings offers 15 s, 30 s, a minute, 5 minutes and Never, which is 0) with nothing going on, Milo leaves (ADR 24). `Presence` (owned by `MiloModel`) decides. "Something going on" is `Presence.needs`: any state but idle, a bubble (his words, a nudge, a reminder, a note), a question, `canStop`, the voice capsule (a key down, hands-free, "Pasted"), an active helper, hands work or a borrowed mouse, looking, a meeting that records or whose notes he writes, a working window, a fly target or any flight. The user dragging him counts too, and a pointer resting on him when the wait ends holds him a few seconds more. Being offline doesn't count. The wait starts when the last of these ends. Presence follows the model's `objectWillChange` (and the meeting's), looking a moment later once the change is in, so every way the model changes is covered without hooks in each. Some things bring him back at once instead of waiting for that look: the talk or dictate key (`MiloModel.press`), a click on him, opening the menu bar menu and "Move Milo back to the corner". "Hide Milo" in the menu sends him off now, but only while nothing needs him; he comes back like after a wait. Leaving, the wren crouches (his takeoff), hops about 30 pt and dives off past the panel's bottom-right corner, faster and faster, fading as he nears the edge. Coming back runs the same path backwards: he swoops in, rises past his perch and lands. `Presence.Pose` is a pure function of time, so the panel draws it with a `TimelineView` only while he moves, and `OverlayRenderTests.renderLeavingAndComingBack` pins any frame. Turning round halfway starts from where he is. The bubble, capsules, Stop and the helper birds fade with him and are back at once when he returns, so Yes and Allow can be clicked while he is still flying in. With Reduce Motion it is a 0.25 s fade. `OverlayPanel` orders itself out once he is away, so an invisible panel takes no clicks, and in again as soon as he starts back. The move is inside the panel, not the panel itself, so it never fights `FlightDriver`, and he never leaves while a flight is on.

Shared sizes (radii, text width, edge, shadow) are in `Views/Surface.swift`. Increase Contrast makes the paper opaque and the edges real lines; Reduce Motion turns scales into fades and stops the dots and the outline from moving. `OverlayRenderTests` renders every moment in light and dark.

## Themes

Milo has one theme, and every surface around him uses it: the bubble, the live words, the Milo window, the Settings and setup windows, the menu bar sign. Other overlays (the cursor, the working outline, helpers) should use it too.

```swift
let theme = Theme.milo              // or model.theme
theme.primary  theme.tint  theme.accent  theme.ink  theme.glow   // SwiftUI Colors, light and dark built in
theme.onPrimary  theme.card  theme.rule                          // text on primary, cards on tint, hairlines
theme.appKit.primary                                             // the same colours as NSColor, for AppKit
theme.motion.spring  theme.motion.gentle                         // his springs; never linear tweens
theme.motion.animation(reduced: reduceMotion)                    // a short fade under Reduce Motion
theme.motion.bob                                                 // how far decorative things float

someView.themed(by: model)                     // puts model.theme in the environment
@Environment(\.miloTheme) private var theme    // inside any view below it
```

`primary` is his lavender (buttons, selection, the thread of a task), `tint` a soft wash of it (window paper), `accent` the marigold of his scarf, `ink` text on `tint`, `glow` halos and highlights. The API lives in `app/Sources/MiloKit/Theme.swift`; add a colour there rather than in a view. Windows use `.themed(by:)`; the always-there overlay panels (the cursor, the working outline, the borrowed-mouse frame) pass `Theme.milo` into their view. Task status colours (running, done, failed, needs you) are their own. There is no setting for his look any more: `[ui] character` is gone from the template and from `ui_config`, and an old config.toml that still has it (`pip`, `classic`, …) loads with a warning that the key is ignored.

## Meeting notes

See [docs/design/meetings.md](design/meetings.md) and [docs/research/meetings.md](research/meetings.md).

- **The app records, the brain decides.** `Meetings/MeetingController` polls `CallSignals` (`Adapters/MacCallSignals`: who uses the mic, from Core Audio's process list, and browser window titles) and turns them into `call_started` and `call_ended` through the pure `CallDetector`. The brain's `MeetingService` asks once through `Approvals` ("Looks like a meeting. Should I take notes?", shown, not spoken) or starts on its own for `[meetings] auto = "calendar"` when the calendar has an event now. It sends `meeting_record` with the folder. The app's `MeetingRecorder` (`Adapters/MacMeetingRecorder`) writes two tracks, `me` (the mic) and `them` (a Core Audio process tap of everything but Milo and the brain, or ScreenCaptureKit), as 30 s WAV chunks through `Meetings/ChunkWriter`, and sends `meeting_chunk` for each one on disk. `meeting_recording` says which tracks are recorded, on every connect too, so a restarted brain goes on with the meeting the app is still recording. While it records, Milo holds a notepad (`FigureInput.noting`), the `MeetingCapsule` over him shows the time with Pause and Stop, and the menu bar shows the time; Stop ends the recording in the app at once and sends `meeting_toggle`, Pause silences the recorder and sends `meeting_pause`. The question's "Always for Zoom" and "Never for Zoom" (`confirm` `choices`) are kept in `[meetings] always` and `never` through `Settings.change`.
- **Passes.** `MeetingService` transcribes the track furthest behind in passes of up to 30 s, cut at the quietest moment, with `TimedTranscriber.words` (Whisper word times) through `BackgroundStt`, which waits while the user dictates or talks. When a dictate or talk key goes down, `Listening.start` calls `BackgroundStt.yield_now` before it queues `wake()`: a meeting call running on the STT thread ends with `Transcriber.interrupt()`, and one still waiting there never starts. The service rolls the speaker tracker back and runs that same pass again first, once the user is done, so the user's passes never wait on a meeting. Each pass appends its lines and a progress mark to `meetings/<id>/transcript.jsonl` in one write (`MeetingStore`), and re-renders `transcript.md`. A crash repeats at most the pass it was in, and its lines count once.
- **Speakers.** The `them` track's Whisper segments go to the `Diarizer` (`DIARIZERS` registry, `[meetings] diarizer`), one voice embedding each. `SpeakerTracker` keeps the meeting's voices across passes. Names come from `VoiceBook` (voices the user named before), the calendar (one attendee and one voice), and the user ("that was Anna", "Speaker 2 is Tom").
- **During the call.** LiveTalk asks `MeetingService.before_turn(text)` for a `<meeting>` block with what was said, newest last and escaped, and treats it like screen data: untrusted, and the conversation counts as tainted.
- **What the app shows.** `MeetingService` sends `meeting_status` on every change (phase, time, speakers, the writing step, an error with its fix), `meeting_lines` as passes land (cleaned of private and paused stretches), and `meeting_notes` once `notes.md` is written. The app keeps them in `Meetings/MeetingModel`; a meeting conversation's page is `Views/MeetingPage` (live transcript, then notes, to-dos and transcript tabs), and `open_meeting` asks for whatever a page needs. The meeting has one conversation from start to notes (`Transcript.meeting`), so questions asked on its page go there.
- **After.** A fresh chat-model session writes the summary, decisions, to-dos and a follow-up draft as JSON (`meeting_text.SUMMARY_RULES`). The brain writes `notes.md`, deletes the audio unless `[meetings] keep_audio`, adds to-dos to Reminders and drafts the mail when the page asks (`meeting_todo`, `meeting_mail`; the draft goes to a careful helper with the meeting text as data), and records a `meeting` episode in memory (`Memory.record` through `on_episode`): the title and summary, the people named, the app, `source` `meeting:<id>`, untrusted because it's other people's words.


## Heartbeat cost model

The heartbeat must not burn tokens. One tick does a `stat()` on `reminders.md`, runs the enabled rules in memory and writes `state/heartbeat.json`. That's zero harness calls. A rule can attach an `llm_prompt` asking for nicer wording, but the runner uses it only if `LlmBudget.allow(today)` is true. The default `llm_calls_per_day = 0` means it never is. `tests/proactive` simulates a full day of ticks and asserts zero calls.

A chat turn costs one message to the running chat model: about 600 tokens, with the first text after 1 to 2 s. A delegated task costs one harness call. Measured with `codex exec` on 2026-10-29: about 19k input tokens for a plain reply (mostly cached on resume) and about 62k when the agent edits memory files. That takes 5 to 10 s. The usage ledger labels these `chat`, `task` and `proactive`. See [ADR 5](adr/0005-live-chat.md).
